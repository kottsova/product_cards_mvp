# Очередь покрытия каталога (Stage 17)

Офлайн-планировщик и исполнитель поверх существующего pipeline. Он отвечает на один вопрос: **какие товары каталога реально готовы к запуску и чего ждут остальные** — и делает это воспроизводимо, без сети, без Chromium и без поисковых систем.

Код: `product_tool/coverage/` (`catalog_units.py`, `facts.py`, `classify.py`, `planner.py`, `executor.py`). Данные Stage 13–16 в машинном виде: `product_tool/config/coverage_planner.v1.json`. Отчёт и артефакты запуска: `reports/source_census_2026-09-24_stage17/`.

## Команды

```powershell
# очередь по каталогу (только чтение каталога, сеть заблокирована на уровне процесса)
.\.venv\Scripts\python.exe -m product_tool.coverage plan --out reports\<каталог> --print-summary

# прирост между двумя очередями (до/после нового адаптера или нового URL)
.\.venv\Scripts\python.exe -m product_tool.coverage delta --before <до>\coverage_units.jsonl --after <после>\coverage_units.jsonl
```

Два запуска `plan` на одном каталоге, конфигурации и состоянии репозитория дают одинаковые байты (нет времени, нет сети, всё отсортировано).

## Единица работы

* **Уникальный товар** — ключ каталога: бренд (без регистра) + категория + артикул продавца. 16 888 единиц; сверка с листами «Контекст» и «Бренд_Категория» обязательна (`reconcile`), при расхождении план не строится.
* **Связка бренд–категория** — 1 058. Статус связки: `ready_to_run`, только если готовы все её товары; иначе преобладающий статус среди неготовых (при равенстве — порядок `pair_tiebreak_order`). Частично готовые связки помечены отдельно (`partially_ready`, `ready_units`).
* Пустой бренд — отдельные единицы (32), а не склейка с одноимённым артикулом другого бренда. Артикул продавца не считается кодом производителя автоматически.

## Статусы

Каждому товару присваивается ровно один статус. Первый подходящий шаг решает:

| # | Условие | Статус |
|---|---|---|
| 1 | нет бренда/артикула, бренд не зарегистрирован или требует ручного решения | `manual_review` |
| 2 | один артикул — отдельные единицы каталога в разных категориях/брендах | риск `seller_sku_shared_across_*`; `identity_conflict` только если названия называют разные модели (Stage 18, `docs/COVERAGE_QUEUE_V18.md`) |
| 3 | Bosch: категория вне маршрутов home/tools | `manual_review` |
| 4 | подтверждённый факт по товару (`product_facts` в конфигурации) | статус факта (сейчас: HyperX `7G7A4AA#ACB`, регион `#ACB` против страницы `#ABA`) |
| 5 | у бренда рабочий адаптер и host остановлен | `host_blocked` |
| 5 | рабочий адаптер и точный URL известен | `ready_to_run` (`url_basis=known_url_map`) |
| 5 | рабочий адаптер с собственным подтверждённым маршрутом поиска (LG) | `ready_to_run` (`url_basis=adapter_discovery`) |
| 5 | рабочий адаптер без URL | `adapter_url_missing` |
| 6 | нет адаптера, официального маршрута нет | `manual_review` |
| 6 | нет адаптера, host остановлен | `host_blocked` |
| 6 | нет адаптера, **для категории этого товара** есть Product page (full-value карточка или структурный образец с identity+specifications+media) на рынке каталога | `official_route_no_adapter` |
| 6 | нет адаптера, для категории страницы нет, она из чужого рынка или неполна | `needs_product_page_fixture` |

**Рабочий адаптер** — класс, на который действительно диспетчеризует `worker.run_once()`: сейчас LG (`lg_kz`, `lg_ru`) и HyperX. Таблица диспетчеризации — константы `worker.LG_BRAND_ALIASES`/`worker.HYPERX_BRAND_ALIASES`; `tests/test_coverage_queue.py::RegistryMatchesWorkerDispatch` прогоняет `run_once()` для каждого алиаса и проверяет, что вызывается именно заявленный адаптер. Исследовательские скрипты `product_tool/census/*` адаптерами не считаются (тест проверяет, что `worker.py` их не подключает).

**Дилеры** (DNS, Sulpak) — только поле `dealer_exact_urls` у единицы и отдельный provenance; они не меняют статус официального маршрута и никогда не записываются в `exact_url`. Технопарк отмечен как `adapter_not_implemented`.

**Остановка host** — из сохранённых журналов (`host_stop_logs` в конфигурации + `data/hyperx_fetch_log.json`, если он есть) по правилу `blocked_hosts_from_fetch_log` (401/403/429) и из профилей `http_blocked`. Один раз остановленный host остаётся остановленным и в новом запуске.

## Исполнитель и checkpoint

`executor.run_units()` передаёт строку каталога в обычный конвейер: строка становится продуктом в jobs-БД, `jobs.enqueue`, затем `worker.run_once()` с теми адаптерами, которые дал вызывающий код. Своей логики поиска у исполнителя нет. Вокруг `run_once()` он добавляет:

* единица не в статусах `ready_to_run`/`adapter_url_missing` в `run_once()` **не передаётся**; в checkpoint пишется точная причина остановки;
* перед каждой единицей заново читаются сохранённые журналы: остановленный host не получает запросов и после перезапуска;
* транспорт по умолчанию — `RefusingSession`: любой запрос отклоняется и записывается (`network_calls_refused`), единица останавливается с `offline_no_fixture_transport`;
* один атомарный файл checkpoint (`os.replace`); повторный проход пропускает завершённые единицы и не делает ни одного вызова.

Исход единицы: `card` (job `done`, с идентификацией, фактами, фото, пробелами и URL evidence), `review` (job `needs_review` + код причины, например `identity_base_code_only`) или `stopped` (код причины: `official_url_needed`, `host_blocked`, `offline_no_fixture_transport`, …).

## Группировка запросов

Пользователю не уходят тысячи одинаковых сообщений. Каждая неготовая единица попадает ровно в одну группу `(статус, причина, бренд/семейство, группа категорий, host)`; группа содержит одно сообщение, число товаров и связок, список категорий и до 5 примеров артикулов. Вид группы: `ask_user` (точные URL), `capture_fixture`, `dev_task` (адаптер), `human_decision` (host, identity, ручная проверка).

## Первые волны адаптеров

`waves.json`: по одной волне на подтверждённый шаблон Product page (группы A–D из readiness map Stage 13, обновлённой Stage 15). Для каждой: текущие статусы, `expected_gain` (сколько единиц и связок перейдёт из «нет адаптера»; сколько гарантированно станет `ready_to_run` благодаря URL, уже подтверждённым exact_variant-доказательствами; верхняя граница через подтверждённый маршрут поиска), предпосылки и критерии готовности адаптера:

1. **identity_exact** — `exact_variant` только при совпадении кода вместе с региональным/сервисным суффиксом;
2. **variants_positive_negative** — положительный и отрицательный вариант на категорию, отрицательный никогда не `exact_variant`;
3. **specifications** — пары имя/значение с URL и evidence;
4. **gallery_complete** — вся галерея именно этого варианта, лишнее исключено с причиной;
5. **documents_evidence** — документ только по прямой ссылке с точной моделью; нормативные документы — не инструкции; пробел называется пробелом;
6. **run_once_offline** — `worker.run_once()` на fixtures даёт ожидаемые `done`/`needs_review`;
7. **checkpoint_resume** — checkpoint исполнителя сохранён, повторный проход без новых вызовов;
8. **policy_fetch** — все запросы через `PolicyAwareFetcher`, остановка host переживает перезапуск;
9. **coverage_delta** — `delta` показывает обещанный переход статусов и ни одного перехода в `ready_to_run` без положительного fixture.

## Запрет сети в тестах: какая команда что гарантирует

Запрет — `tests/_bootstrap.py`: блок `requests.adapters.HTTPAdapter.send` плюс блок `socket.getaddrinfo` и `socket.socket.connect(_ex)` для любых адресов, кроме loopback. Включается один раз на процесс; порядок импорта тестовых модулей значения не имеет, если сработал пакетный путь.

| Команда | Запрет включён до загрузки тестов? |
|---|---|
| `python -m tests` | да, гарантированно (импорт пакета `tests` до discovery) |
| `python -m unittest discover -s tests -t .` (в том числе с `-p`) | да, гарантированно (пакет импортируется при загрузке модулей) |
| `python -m unittest tests.<модуль>` | да, гарантированно |
| `python -m unittest discover -s tests` (прежняя команда) | **только если** `test_000_network_safety.py` попал в набор: он первый по алфавиту и включает запрет при импорте. С `-p` без него запрет **не включён** |

Проверка выполняется тестами `tests/test_000_network_safety.py` (подпроцессы: поздно сортируемый модуль импортируется первым, а запрет уже включён) и скриптом `reports/source_census_2026-09-24_stage17/scripts/04_guard_matrix.py`, результат — `guard_matrix.json`. Исполнитель и CLI планировщика дополнительно используют `product_tool.offline_guard.offline_only()`.

## Что план не утверждает

* `ready_to_run` — это «можно запускать через рабочий адаптер», а не «карточка получится». Для LG (578 единиц) ссылка определяется самим адаптером по sitemap/шаблону; будет ли товар там — покажет запуск.
* Профили `adapter_profiles.v1.json` для Samsung, PlayStation, Microsoft и Razer устарели (Stage 13); их факты переопределены в `coverage_planner.v1.json` со ссылкой на evidence. Stage 18 сузил эти факты до категорий, host и рынка, которые реально наблюдались.
* Факты о дилерах и Технопарке не проверялись: сети в этом этапе нет.
