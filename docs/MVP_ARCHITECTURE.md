# MVP внутреннего инструмента для карточек товаров

Наблюдения о процессе Кати, включая требования к точному варианту модели и фотографии, записаны в [рабочих сценариях](WORKFLOWS_AND_BACKLOG.md). Эти требования входят в общую модель товара и проверку результата; список её категорий добавляется постепенно.

## Решение

Коллега загружает Excel и работает с отдельной партией товаров. Приложение хранит исходные строки, найденные данные и состояние обработки. Python группирует товары по категориям, а парсер обрабатывает каждую группу отдельно. Итог скачивается как Excel с отдельным листом на категорию. Google Sheets не нужна для работы нового продукта.

Текущий личный workflow n8n и исходный парсер пока остаются нетронутыми. Для нового продукта достаточно одного общего workflow n8n: принять идентификатор задания и передать запуск Python-сервису. Выбор бренда, категории и этапов выполняет Python, поэтому отдельные workflow на каждый бренд не нужны.

## Пилотные категории

| Бренд | Категории | Источник примеров |
| --- | --- | --- |
| LG | Стиральные машины, стирально-сушильные машины, паровые шкафы | Приложенный Excel с тремя строками |
| Samsung | Стиральные машины, смартфоны, телевизоры, часы | Нужны обезличенные примеры |
| Apple | Часы, смартфоны, колонки, наушники, ноутбуки | Пример ноутбука дан названием; по остальным нужны примеры |
| Lenovo | Ноутбуки | Пример дан названием |

Это пилотный набор для проверки устройства системы, а не закрытый перечень поддерживаемых категорий. Новые категории добавляются правилами проверки и нормализации данных; новые сайты — адаптерами. Поддержка бренда и поддержка категории — разные задачи.

Первая техническая итерация должна полностью провести через систему три строки LG из образца. После этого добавляются Samsung и Apple с проверкой на примерах каждой категории. «Поддерживается» означает, что товар можно загрузить, найти достаточно точную страницу, собрать данные, увидеть причину пропусков и выгрузить результат. Если точное совпадение не доказано, товар получает статус «Нужна проверка», а не случайную карточку.

## Входной Excel

Формат Excel может отличаться от файла к файлу. Для запуска поиска обязательны **бренд** и **код товара для поиска** (модель или артикул, выбранный при импорте). Штрихкод/EAN и другие поля принимаются как необязательные; их роль в поиске уточняется после изучения работы коллег.

В приложенном образце:

- строка 1 содержит групповые заголовки;
- строка 2 содержит основные заголовки;
- строка 3 уточняет три колонки размеров упаковки;
- товары начинаются со строки 4.

В этом образце колонки нумеруются с 1: **1 — категория («Предмет»), 2 — бренд, 3 — наименование, 4 — артикул продавца, 5 — модель**. Настройка импорта позволяет указать именно номер колонки. Для поиска в этом шаблоне сначала используется колонка 4, затем колонка 5 как запасной код; оба значения сохраняются и сверяются с найденной карточкой, поскольку они не всегда совпадают.

Импортёр распознаёт строки заголовков и предлагает номера колонок для бренда, кода поиска, категории и названия. В предпросмотре коллега подтверждает или меняет это соответствие. Автоматическое определение разрешено только когда оно достаточно однозначно; при сомнении система просит выбрать колонки. Файл без отдельной колонки категории может использовать распознавание по названию товара, но результат обязательно показывается для подтверждения. Исходный файл и все исходные колонки сохраняются. Образец с тремя строками заголовков — первый проверочный случай, а не единственный допустимый шаблон.

При импорте просматриваются первые строки каждого листа, выбирается лист с товарами и находится строка с заголовками. Для типовых названий колонок используются синонимы (`Бренд`, `Марка`, `Производитель`; `Модель`, `Код модели`, `Артикул` и т. п.). Предпросмотр показывает минимум исходную строку, распознанный бренд, код поиска, категорию и номер строки Excel. Если соответствие неоднозначно, запуск блокируется до ручного выбора колонок. Повторяющиеся модели не удаляются автоматически: они могут представлять разные варианты товара.

Отдельный тестовый файл дополняет три полные строки LG пятью строками, где заполнено только название: смартфон Samsung `SM-A566ELIHINS A56 12+256GB`, ноутбуки Lenovo `83M0003YRK` и Apple `MGN63RU`, телевизор Samsung `UE55U8000FUXCE`, наушники Apple `MGYM3RU/A`. Так проверяются оба случая: готовые колонки и извлечение бренда, категории и кода из названия. Коды сохраняются дословно, включая дефис и косую черту. Эти названия являются входными примерами пользователя; совпадение с официальными карточками ещё не проверялось.

Минимальные внутренние входные поля: `brand` и `search_code`. Необязательные поля: `category`, `product_name`, `seller_sku`, `model`, `barcode`, `reference_url` и любые дополнительные колонки из загрузки. Пустое поле сохраняется пустым. Исходная строка и файл остаются доступны для проверки.

Категория берётся из указанной колонки, если она есть. Если её нет, классификатор использует название товара. Например, «стиральная машина с сушкой» проверяется раньше общего правила «стиральная машина». Неуверенная классификация попадает в группу «Категория не определена» и предлагается человеку для исправления до запуска. После подтверждения Python группирует товары по категориям. Предпросмотр и итоговая выгрузка показывают отдельный лист на категорию; обработчик также проходит по группам отдельно. Промежуточный Excel не служит базой состояния процесса.

`seller_sku` и `model` хранятся раздельно: они могут отличаться. Ссылка на магазин из файла служит ориентиром, а найденная официальная страница сохраняется в отдельном поле. Цена, штрихкод и данные об упаковке, если они есть, остаются исходными данными и не перезаписываются найденным текстом. Размеры упаковки не подменяют размеры продукта.

## Обработка одной строки

1. Нормализовать бренд и выбранный код поиска, сохранив исходные значения; определить категорию.
2. Найти модель на официальном сайте бренда способом, подходящим именно этому сайту. Для LG сохранить проверенный путь режима 6: sitemap, точное совпадение модели, проверка страницы.
3. Проверить совпадение модели и варианта товара. Для неоднозначного результата показать кандидатов человеку.
4. Извлечь характеристики и описание отдельными этапами, как в режимах 7 и 8 LG, затем фото по логике режима 9.
5. Привести найденные названия характеристик к внутренним полям; неизвестные сохранить отдельно, не теряя исходный текст.
6. Если категория известна, проверить её обязательные поля и записать причины пропусков. Отсутствие категории не мешает искать модель, но оставляет проверку категории на потом.
7. Сохранить ссылки на источники каждого найденного значения.

Для LG переносится проверенный поиск по sitemap и извлечение с `lg.com/kz` из существующего скрипта без изменения логики совпадения. Меняется источник входных строк и место сохранения результата: вместо фиксированной Google Sheet используется партия в приложении. Для Samsung и Apple сохраняются те же три этапа «ссылка → характеристики → описание», но реализация поиска и чтения страницы будет специфичной для каждого сайта. Общий извлекатель может быть запасным способом; его результат проходит такую же проверку точного совпадения.

Из существующего скрипта LG переиспользуются точные функции работы с sitemap, проверки карточки и извлечения данных; весь файл с 19 режимами не переносится целиком. Проверка ошибок запуска меняется так, чтобы технический сбой не отображался как успешная обработка.

Каждый адаптер сайта предоставляет одинаковые операции. Для первого теста они соответствуют режимам LG 6–9, но в интерфейсе получают единые номера 1–4. Дополнительно закладываются 5 — поиск видео и 6 — поиск инструкции. Адаптеры можно разместить в отдельных файлах `lg.py`, `samsung.py`, `apple.py`; общий запускатель выбирает файл по бренду. Он запускает только выбранные этапы и сохраняет причины, если источник не поддерживает видео или инструкцию.

| Этап | Что ищем |
| --- | --- |
| 1 | Официальная страница модели и ссылка |
| 2 | Описание |
| 3 | Характеристики |
| 4 | Фото |
| 5 | Видео |
| 6 | Инструкция |

Перед запуском человек выбирает «Все» или отмечает нужные этапы. Если выбран этап 2–6, а официальной ссылки ещё нет, этап 1 выполняется как необходимый предварительный поиск; другие невыбранные поля не заполняются. По умолчанию повторный запуск заполняет пустые поля и сохраняет уже подтверждённые значения.

## Состояния и интерфейс

Партия: `загружена → в очереди → обрабатывается → готова / готова с вопросами / ошибка`.

Товар: `ожидает → поиск → извлечение → готов / нужна проверка / не найден / ошибка сайта`.

Ошибка загрузки файла показывается до создания партии. Отсутствие характеристики и ошибка сайта различаются. Повторная попытка обработки товара не стирает уже подтверждённые входные данные. После перезапуска сервиса незавершённые задания должны продолжаться или получать понятное состояние, а не зависать навсегда.

Основные экраны: загрузка и предпросмотр; список партий; таблица товаров с фильтрами по состоянию; карточка товара с исходными и найденными значениями, источниками и ручным исправлением; скачивание Excel.

Экспорт содержит исходные колонки, добавленные результаты, состояние проверки и ссылки на источники. Товары разных категорий располагаются на отдельных листах, а исходные строки сохраняют ссылку на свой номер в загруженном файле. Это промежуточный результат перед ручной работой в ChatGPT, а не автоматически готовая карточка Wildberries.

## Сервисы и границы

```text
Браузер → FastAPI → база партий и товаров ← отдельный Python worker
                    ↑                         ↓
               исходные Excel          адаптеры сайтов
                    ↓
               экспорт Excel
```

- **FastAPI** принимает файл, показывает предпросмотр, создаёт партию, отдаёт состояния, позволяет исправления и создаёт Excel.
- **Worker** последовательно обрабатывает товары и записывает прогресс. Долгий парсинг не выполняется внутри HTTP-запроса.
- **База** хранит партии, товары, результаты, статусы и источники. Для одного VPS и одного worker на первом этапе достаточно SQLite с резервными копиями.
- **n8n** выполняет один общий стартовый workflow: получает `job_id`, вызывает внутренний HTTP endpoint Python-сервиса и при необходимости выполняет последующие интеграции. Скрипты по имени и режиму n8n напрямую не запускает; выбор адаптера и этапов делает Python.
- **Caddy** позже обеспечивает HTTPS и доступ коллег к сайту. Секреты находятся в переменных окружения или файлах, не включаемых в образ и репозиторий.

## Где собираем и как открываем без домена

Сначала приложение собирается и проверяется на рабочем ПК в отдельной папке от текущего парсера. Веб-страница и API обслуживаются одним FastAPI-приложением; отдельная сложная система сборки фронтенда для первого этапа не требуется.

- `localhost` открывается только на том же ПК.
- Коллеги находятся в разных сетях, поэтому адрес вида `http://IP-вашего-ПК:порт` не выбран для совместного теста.
- Закрытый тест без собственного домена: Tailscale Serve даёт частный HTTPS-адрес. Коллеги должны войти в разрешённую частную сеть.
- Для первого теста выбран вариант «ссылка и логин»: Tailscale Funnel даёт публичный HTTPS-адрес без собственного домена, а приложение требует входа. Коллегам устанавливать Tailscale не нужно. Этот способ подходит для пилота, а не заменяет решение о постоянном размещении.
- Рабочий ПК должен быть включён во время любого локального размещения. Постоянно доступный сервис позднее переносится на VPS. Собственный домен не нужен для разработки и первых тестов.

Планируемые API: `POST /api/batches` (загрузка), `GET /api/batches/{id}/preview`, `PATCH /api/batches/{id}/mapping` (номера колонок и категории), `POST /api/batches/{id}/run` (выбранные этапы 1–6), `GET /api/batches/{id}`, `GET /api/batches/{id}/products`, `PATCH /api/products/{id}` (ручная правка), `GET /api/batches/{id}/export.xlsx`.

## Очерёдность сборки

1. Гибкий импортёр Excel: определение колонок бренда и модели, ручное подтверждение, сохранение всех исходных значений; приложенный файл — проверочный случай.
2. Партии, состояния и отдельный worker без доступа к Google Sheets.
3. Перенос режимов LG 6–9 в адаптер и проверка трёх предоставленных товаров, включая фото.
4. Шесть выбираемых этапов в интерфейсе; поиск видео и инструкций с явным состоянием «не поддерживается» там, где адаптер ещё не готов.
5. Примеры Samsung и Apple; адаптеры сайтов и правила категорий.
6. Экран проверки, ручные исправления и экспорт Excel с отдельными листами категорий.
7. Docker, вход по логину и резервное копирование после сквозной проверки локально. Затем открыть удалённый пилот через Tailscale Funnel. VPS нужен позже, если потребуется постоянно доступный сервис без зависимости от включённого рабочего ПК.

## Открытые вопросы перед правилами проверки

- Нужны примеры хотя бы по одному товару в каждой пилотной категории Samsung и Apple, особенно варианты цвета, памяти, размера и регионального кода.
- Для каждой категории нужно согласовать, какие поля обязательны именно для внутренней готовности, а какие можно оставить на ручную доработку в ChatGPT.
- Нужно решить, могут ли коллеги исправлять найденные данные в инструменте; текущий план предусматривает такую правку.
